01 / THE PROBLEM

A business metric dropped. What should an analyst investigate next?

The solution

Evidence Atlas brings the outcome, ranked factors, source statistics, and missing-data guidance into one investigation. The objective is to support the next analytical decision while keeping uncertainty visible.

Implementation scope

The project brings together a FastAPI investigation service, CSV validation and profiling, a JavaScript workspace, evidence inspection, and report export. The linked implementation and tests document those components.

03 / ENGINEERING DECISIONS

The reasoning behind the build.

01

Repeatable analysis

The Python analysis uses explicit statistical rules rather than asking an LLM to invent explanations. The same data and target produce a reproducible investigation; the analysis remains limited by those rules.

02

Confidence with boundaries

Pearson relationships support ranking, not causal proof. The causal-readiness score uses dataset characteristics and column-name heuristics; it is not a calibrated probability or a treatment-effect estimate.

03

Validate time before analysis

Recognised date columns are parsed and sorted, with duplicate timestamps rejected. This prevents file row order from defining the latest observation.

04

Protect the API boundary

Configurable sign-in, sessions, host validation, CSV limits, and per-client rate limits provide application safeguards. These controls depend on deployment configuration.

05 / CHALLENGES ADDRESSED

Where the engineering matters.

Unsorted CSVs change the apparent latest value

Constraint
The pipeline cannot assume that the final row is the latest timestamp.
Implementation
Validate recognised timestamps and sort them before analysis.
Takeaway
Data ordering is part of the investigation contract.

What-if has no usable independent factor

Constraint
A dataset containing only the outcome cannot support a separate-factor scenario.
Implementation
Return an unavailable state and reject an invalid simulation request.
Takeaway
An understandable unavailable state is better than an unsupported estimate.

06 / BOUNDARIES

What comes next.

Current limitations

  • Observational ranking cannot establish cause and effect.
  • The confidence scores are heuristic and are not calibrated probabilities.
  • The rate limiter is single-process; multiple replicas require shared enforcement.
  • Shared-password access needs SSO/OIDC before enterprise multi-user use.
  • Durable investigation storage and formal causal estimators are future work.

Next engineering steps

  1. Add persistent investigation storage and SQL/API connectors.
  2. Use validated cohorts and assumptions before introducing causal estimators.
  3. Add shared rate limiting and organisation authentication.

THE TAKEAWAY

The quality of an analytical product depends on what it refuses to conclude as much as what it can calculate. Input validation, traceable evidence, and explicit limitations are part of the result.
