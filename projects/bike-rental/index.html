03 / ENGINEERING DECISIONS

The reasoning behind the build.

01

Represent periodic time

Sine and cosine encode hour and month so adjacent cycle boundaries remain close. Rush-hour and weekend flags add interpretable calendar signals.

02

Remove direct target components

The training scripts exclude casual and registered counts, whose sum is the demand target. Including them would leak the answer into the inputs.

03

Use historical demand carefully

The advanced script sorts observations and shifts demand for lag and rolling features. Its outer split uses the earlier 80% for training and later 20% for testing.

04

Explain error as well as predictions

Residual plots and quantile regression complement R², MAE, and RMSE. A nominal 90% interval is a target range, not a claim of verified 90% coverage.

Evaluation approach

  • Compare Gradient Boosting and XGBoost using R², MAE, and RMSE.
  • Evaluate advanced models on a chronological outer holdout.
  • Inspect residual patterns and SHAP values on a held-out sample.
  • Calculate interval coverage on a test subset in the analysis script.

These are evaluation procedures in the repository, not an automated API test suite. The displayed scores are repository-reported outputs and have not been re-trained during this portfolio update.

05 / CHALLENGES ADDRESSED

Where the engineering matters.

Calendar boundaries hide useful structure

Constraint
Raw hour numbers place 23 and 0 far apart despite being adjacent.
Implementation
Add sine/cosine encodings and explicit calendar flags.
Takeaway
Features should represent the structure of the problem.

A strong score can conceal forecasting constraints

Constraint
Lagged demand needs historical observations at prediction time.
Implementation
Document the chronological holdout and the availability of lag inputs.
Takeaway
Evaluation should describe the actual forecasting situation.

06 / BOUNDARIES

What comes next.

Current limitations

  • Lag inputs must be available when a prediction is made; these results do not establish multi-step forecasting performance.
  • Initial lag values are filled with medians before the outer split, so preprocessing is not fully isolated to training data.
  • The advanced hyperparameter search uses ordinary three-fold CV, not a time-series-aware inner split.
  • Earlier baseline results use a random split and should not be compared as if the evaluation setup were identical.
  • Reported prediction intervals need calibration checks across time and demand regimes.

Next engineering steps

  1. Move imputation into a training-only pipeline.
  2. Use time-series-aware tuning and walk-forward validation.
  3. Benchmark one-step and multi-step forecasts separately.

THE TAKEAWAY

A useful forecast needs a transparent evaluation setup. Explainability and uncertainty are valuable only when the data available at prediction time is clearly defined.
